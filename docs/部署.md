## 上线前检查清单

按顺序做，做完一条勾一条。标【真用】的只有给真实门店用时才必须做，演示站可以跳过。

1. **【真用】关掉演示模式**：`.env` 里写 `DEMO_MODE=0`。关掉后 hq、regional、manager、staff 不再受保护、登录页不再显示演示账号、`pnpm db:reset` 拒绝执行。然后马上用 hq 登录，把这 4 个账号（密码 `demo1234` 是公开的）全部改密码或停用；模拟数据里其他员工的密码也都是 `demo1234`，不要用 `db:reset` 灌模拟数据，自己建门店和账号。也不要配“每天重置”。
2. **密钥**：`SESSION_SECRET` 和 `POSTGRES_PASSWORD` 各用 `openssl rand -base64 32` 生成。`SESSION_SECRET` 少于 32 个字符、还是示例占位值，应用会拒绝启动。
3. **第一次实跑 Docker**：按下面“第一次部署”走一遍，确认 `docker compose ps` 里 app 显示 healthy、`curl http://服务器IP/api/health` 返回 `{"ok":true}`、能登录。镜像和 compose 至今没实际跑过，这一步发现问题就当场改。
4. **HTTPS**：备案下来后 `SITE_ADDRESS` 换成域名，Caddy 自动申请证书（见下面“有域名以后”）。HSTS 和登录 cookie 的 Secure 会自动生效。
5. **备份**：`backup` 服务每天 03:00 备份到 `./backups`、留 14 天。上线当天手动跑一次 `docker compose exec backup sh /backup.sh now`，确认 `./backups` 里有文件；再按下面“恢复演练”在临时库里恢复一次。
6. **备份异地**：`./backups` 和数据库在同一块盘上，盘坏了一起丢。在宿主机配一个每天的定时任务，把 `./backups` 同步到对象存储（阿里云 OSS 用 `ossutil sync`，或 `rclone sync`），桶开版本保留。
7. **【真用】升级前先备份**：Prisma 迁移没有回退，每次更新代码前先手动备份一份（见下面“更新代码”）。
8. **健康拨测**：在云监控或 UptimeRobot 一类服务里配一个拨测，每分钟请求 `https://你的域名/api/health`，连续失败就发短信或邮件；数据库不通时它返回 503。再配一个磁盘使用率超过 80% 告警。
9. **【真用】每天对账**：宿主机定时任务每天跑 `docker compose run --rm tools pnpm db:check`，退出码不是 0 就告警。它检查配件余额 = 流水累计、机器数 = 流水累计、收款 = 应收、已确认日结 = 当天收款、机器状态 = 流水、服务权益 = 单据。
9b. **智能提醒**（口径第 18 节）：宿主机定时任务每天 09:00、21:00 跑 `docker compose run --rm tools pnpm alerts:run`，生成今日待办、发系统内消息；要推企业微信门店群，`.env` 写 `ALERT_PUSH_ENABLED=1`，再在组织管理里给门店填群机器人地址。
9a. **每日任务**：宿主机定时任务每天 09:00 跑 `docker compose run --rm tools pnpm daily`（生成碎屏险、延保的到期提醒；删掉 180 天以前的微信客服消息；真对接企业微信时还重放处理失败的回调、删掉过期没扫的开单二维码配置、提交离职继承和查客户继承的结果），退出码不是 0 就告警。漏跑一天也不会漏人（按区间补），但到期名单上的“待联系”会晚一天出来。
10. **日志**：`docker compose logs app`、`logs caddy`（Caddy 记每个请求）。每个容器日志最多 5 个文件 × 50MB，自动滚动。
11. **登录限流**：compose 里给 app 设了 `TRUST_PROXY=1`（在 Caddy 后面，来源 IP 可信），按“IP + 用户名”限流，同一 IP 累计错 20 次也锁。限流状态在内存里，重启清零；**【真用】**多台应用服务器时要换成数据库或 Redis，对外开放的话再加验证码。
12. **性能**：单台 4 核实测 10 并发看总部看板 p50 约 1 秒、30 并发约 2.7 秒、0 错误，单进程 Node 是瓶颈。10 家店够用；**【真用】**到 50 家店、上千人时要多开几个应用实例让 Caddy 分流，或换更大的机器，总部看板和收银日报做缓存或预先汇总。压测方法：`docker compose run --rm -e LOAD_BASE=http://app:3000 tools pnpm load-test 10 10`（见 `scripts/load-test.ts`）。
13. **服务器安全**：安全组只开 80、443 和 SSH；SSH 只允许密钥登录；系统定期更新（见《服务器与备案指引》）。
15. **企业微信（只有要真对接时）**：
    - 前提：企业微信企业已注册（未认证的企业全公司最多加 100 个客户、部分接口受限）；回调地址要公网域名（不能写 IP）。
    - 企业微信后台建一个自建应用，记下 AgentId 和 Secret；在“客户联系”里把它设为“可调用接口的应用”；应用的可见范围包含所有店员。
    - 应用里配“企业可信 IP”填服务器公网 IP（2022 年以后新建的应用不配调不了接口，报 60020）。
    - 应用的“接收消息”配回调：URL 填 `https://你的域名/api/wecom/callback`，Token 和 EncodingAESKey 随机生成，同样写进 `.env`；“客户联系”的回调也指向这个应用。保存时企业微信会发一次验证请求，应用要先跑着且 `WECOM_ENABLED=1`。
    - `.env` 写 `WECOM_ENABLED=1`、`WECOM_CORP_ID`、`WECOM_APP_SECRET`、`WECOM_AGENT_ID`、`WECOM_CALLBACK_TOKEN`、`WECOM_CALLBACK_AES_KEY`，少一项应用拒绝启动。
    - **企业微信后台不要给这些员工配“新客户欢迎语”**：配了的话回调里就没有 welcome_code，系统发不了带保修提醒的欢迎语。
    - 组织管理里给每个店员填企业微信账号（userid），真对接时保存会去企业微信核对。
    - 聊天侧边栏（口径第 12 节第三步）：应用管理 → 本应用 → 配置到聊天工具栏，页面地址填 `https://你的域名/wecom-app/customer`；应用设“可信域名”（要和企业主体一致的备案域名，放校验文件）、“网页授权及 JS-SDK”填同一个域名。员工从工具栏打开时先走网页授权（`/wecom-app/auth`），不用登录 ERP。侧边栏页面允许被本站框住；真机如果显示被拒绝嵌入，再按实测给 `frame-ancestors` 加企业微信的域名。
    - 微信客服（口径第 12 节第三步）：企业微信后台“微信客服”里建客服账号，在“通过 API 管理微信客服账号”里选本应用；客服的消息事件走同一个回调地址（`/api/wecom/callback`）。接待人员和分配规则在企业微信后台配，系统转人工时把客户放进待接入池。客服账号的二维码、链接贴到门店海报和欢迎语里。客服消息留 180 天（每日任务清理），客户的消息不发给任何第三方（这一版没接大模型）。
    - 客户继承（口径第 12 节第三步）：员工离职时先在组织管理停用（马上生效、选接手人），再到企业微信后台把这个人从通讯录删掉；每日任务看到删了就提交离职继承，第二天起查结果。在职转接从客户详情发起，客户 24 小时内可以拒绝。
    - 自动打标、群发这一版没做（见口径第 12 节）。
14. **【真用】已知限制，真用前评估要不要补**（演示版接受，取舍记录里有原因）：
    - 总部账号什么都能做，没有岗位分离（采购、财务分开），登录没有二次验证；
    - 客户表全公司共享，店员能搜到别家店的客户（手机号脱敏显示）；
    - 手机号在数据库和备份里是明文；
    - 数据库账号 `erp` 是这个容器里的超级用户，没有单独的只读、业务账号；
    - 操作日志、库存流水只增不删，没有归档；
    - `/api/session/clear`（清登录 cookie）是 GET，别的网站可以让人被登出（只能登出，不能登录或改数据）；
    - 没有自动部署和回滚脚本；权限矩阵、退货、调拨、盘点没有端到端测试（有服务层测试）。

## 结构

一台服务器、一个 `docker compose`：

| 服务 | 干什么 |
|---|---|
| `db` | PostgreSQL 17，数据存在 `pgdata` 卷里 |
| `app` | 本仓库的 Next.js 应用（`Dockerfile` 三段构建，standalone 输出）；带健康检查（`/api/health`） |
| `caddy` | 反向代理 + 访问日志；`SITE_ADDRESS` 是 `:80` 时用 IP 访问，是域名时自动申请 HTTPS 证书 |
| `backup` | 每天 03:00 用 `pg_dump` 备份到 `./backups`，留 14 天（`docker/backup.sh`） |
| `tools` | 平时不启动；跑迁移、灌演示数据、对账、每日任务（`pnpm daily`）时临时用 |

环境变量（都写在服务器上的 `.env`，不进仓库）：

| 变量 | 说明 |
|---|---|
| `POSTGRES_PASSWORD` | 数据库密码，随机长串 |
| `SESSION_SECRET` | 登录令牌签名密钥，至少 32 个字符 |
| `SITE_ADDRESS` | `:80` 或域名 |
| `DEMO_MODE` | 必填：`1` 演示站，`0` 真用；不写应用拒绝启动，写 1 启动时打提醒 |
| `WECOM_ENABLED` | `1` 真对接企业微信；不写或 `0`：演示站是模拟模式，真用时整个模块不显示 |
| `WECOM_CORP_ID`、`WECOM_APP_SECRET`、`WECOM_AGENT_ID` | 企业 ID、自建应用的 Secret 和 AgentId（只用这一个 Secret） |
| `WECOM_CALLBACK_TOKEN`、`WECOM_CALLBACK_AES_KEY` | 回调的 Token 和 43 位 EncodingAESKey |

## 第一次部署

```bash
# 1. 服务器上装 Docker（Ubuntu 24.04）
curl -fsSL https://get.docker.com | sh

# 2. 拉代码
git clone https://github.com/2770419748-lgtm/dianyoushu-erp.git && cd dianyoushu-erp

# 3. 写 .env（不进仓库）
# 两个随机串用 openssl rand -base64 32 各生成一个（SESSION_SECRET 少于 32 个字符应用会拒绝启动）
cat > .env <<'ENV'
POSTGRES_PASSWORD=换成一长串随机字符
SESSION_SECRET=换成另一长串随机字符
SITE_ADDRESS=:80
DEMO_MODE=1
ENV

# 4. 起数据库、建表；演示站再灌演示数据（约 1 分钟）
docker compose up -d db
docker compose run --rm tools pnpm exec prisma migrate deploy
docker compose run --rm tools pnpm db:reset      # 只有演示站跑；DEMO_MODE=0 时会拒绝

# 5. 起应用、Caddy、备份
docker compose up -d --build app caddy backup
docker compose ps                                  # app 要显示 healthy
curl -s http://127.0.0.1/api/health                # {"ok":true}
```

浏览器打开 `http://服务器IP`，用 README 里的演示账号登录（登录 cookie 会按实际协议决定要不要加 Secure，纯 http 也能登录；上了 HTTPS 后自动加）。应用起不来时先看 `docker compose logs app`：配置不合格（会话密钥太短、还是占位值、没配数据库）会打印“配置不合格，拒绝启动”和具体原因。

## 恢复演练

在临时库里恢复，不动正在用的库：

```bash
docker compose exec db createdb -U erp restore_check
docker compose exec -T db pg_restore -U erp -d restore_check --no-owner < backups/某个备份.dump
docker compose exec db psql -U erp -d restore_check -c "select count(*) from sales_orders"
docker compose exec db dropdb -U erp restore_check
```

真出事要覆盖正式库：先 `docker compose stop app`，再把上面的 `-d restore_check` 换成 `-d dianyoushu_erp --clean --if-exists`，恢复完 `docker compose start app`。
