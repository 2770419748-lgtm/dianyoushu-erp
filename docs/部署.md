## 上线前检查清单

按顺序做，做完一条勾一条。标【真用】的只有给真实门店用时才必须做，演示站可以跳过。

1. **【真用】关掉演示模式、开户**：`.env` 里写 `DEMO_MODE=0`（`pnpm db:reset` 会拒绝执行，也不要配“每天重置”）。建表后在空库上跑开户脚本（见下面“开户、续费、停用”），不灌模拟数据：模拟数据里的员工密码都是公开的 `demo1234`。如果是把演示站改成真用，先清库再开户，别在演示数据上直接用。
2. **密钥**：三个数据库密码 `POSTGRES_PASSWORD`、`APP_DB_PASSWORD`、`READONLY_DB_PASSWORD` 用 `openssl rand -hex 32` 生成（只有数字和字母；base64 会带 `/`，拼进连接串后迁移、应用都连不上，报 P1013 invalid port）；`SESSION_SECRET`、`BACKUP_PASSPHRASE`、`DATA_ENCRYPTION_KEY`、`DATA_INDEX_KEY` 用 `openssl rand -base64 32` 生成（后两把是个人信息加密的钥匙，口径第 20 节，两把不能一样）。`SESSION_SECRET` 少于 32 个字符、还是示例占位值，两把数据钥匙没配、格式不对或用了开发和 CI 的公开值，应用都会拒绝启动。**`DATA_ENCRYPTION_KEY`、`DATA_INDEX_KEY` 另外离线存一份**（打印或存到不在这台服务器上的密码管理器）：加密钥匙丢了，手机号、身份证号就再也解不开。`BACKUP_PASSPHRASE` 也一样，丢了备份打不开。
2a. **【真用】二次验证**：`DEMO_MODE=0` 时店长、区域经理、总部第一次登录要先用手机验证器 App 扫码绑定（口径第 20 节）。开户后让客户老板马上用 `admin` 登录（先扫码绑定，再改初始密码），再建第二个总部账号也绑定上，互为备份：手机丢了由另一个总部在组织管理里“重置二次验证”。只有一个总部又丢了手机时，在服务器上跑 `docker compose run --rm tools pnpm mfa:reset admin "手机丢了"`。
3. **第一次实跑 Docker**：按下面“第一次部署”走一遍，确认 `docker compose ps` 里 app 显示 healthy、`curl http://服务器IP/api/health` 返回 `{"ok":true}`、能登录。镜像和 compose 至今没实际跑过，这一步发现问题就当场改。
4. **HTTPS**：备案下来后 `SITE_ADDRESS` 换成域名，Caddy 自动申请证书（见下面“有域名以后”）。HSTS 和登录 cookie 的 Secure 会自动生效。
5. **备份**：`backup` 服务每天 03:00 备份到 `./backups`、留 14 天。上线当天手动跑一次 `docker compose exec backup bash /backup.sh now`，确认 `./backups` 里有文件；再按下面“恢复演练”在临时库里恢复一次。
6. **备份异地**：`./backups` 和数据库在同一块盘上，盘坏了一起丢。每天把备份同步到另一个地域的对象存储，桶开版本保留：一台放几家时用 `deploy/offsite-sync.sh`（见“一台服务器放几家客户”和“买了服务器以后要做的”第 5 条）。
7. **【真用】升级前先备份**：Prisma 迁移没有回退，每次更新代码前先手动备份一份（见下面“更新代码”）。
8. **健康拨测**：在云监控或 UptimeRobot 一类服务里配一个拨测，每分钟请求 `https://你的域名/api/health`，连续失败就发短信或邮件；数据库不通时它返回 503。服务器上另有 `deploy/health-check.sh` 每分钟巡检（健康检查、定时任务有没有在跑、硬盘 80%），告警发到运维群机器人。
9. **【真用】每天对账**：宿主机定时任务每天跑对账（一台放几家时 `deploy/run-all.sh db:check`，模板 `deploy/crontab.example`），退出码不是 0 就告警。它检查配件余额 = 流水累计、机器数 = 流水累计、收款 = 应收、已确认日结 = 当天收款、机器状态 = 流水、服务权益 = 单据。
9c. **大模型**（口径第 18 节，可选）：在 DeepSeek（或阿里云百炼的通义千问）注册、实名、充值几十元，后台设消费上限，创建 API Key；`.env` 写 `LLM_ENABLED=1`、`LLM_BASE_URL`（如 `https://api.deepseek.com`，必须 https）、`LLM_API_KEY`、`LLM_MODEL`（如 `deepseek-chat`），重启应用。打开了却缺一项，应用拒绝启动。之后“智能提醒”页总部能看到今天调了几次、用了多少 token；模型出错、超时、超过 `LLM_DAILY_LIMIT` 都会自动改发模板版。门店员工内部使用，不用做大模型备案；客户姓名电话不发给模型。
9b. **智能提醒**（口径第 18 节）：宿主机定时任务每天 09:00、21:00 跑 `docker compose run --rm tools pnpm alerts:run`，生成今日待办、发系统内消息；要推企业微信门店群，`.env` 写 `ALERT_PUSH_ENABLED=1`，再在组织管理里给门店填群机器人地址。
9a. **每日任务**：宿主机定时任务每天 09:00 跑 `docker compose run --rm tools pnpm daily`（生成碎屏险、延保的到期提醒；删掉 180 天以前的微信客服消息；真对接企业微信时还重放处理失败的回调、删掉过期没扫的开单二维码配置、提交离职继承和查客户继承的结果），退出码不是 0 就告警。漏跑一天也不会漏人（按区间补），但到期名单上的“待联系”会晚一天出来。
10. **日志**：`docker compose logs app`、`logs caddy`（Caddy 记每个请求）。每个容器日志最多 5 个文件 × 50MB，自动滚动。
11. **登录限流**：compose 里给 app 设了 `TRUST_PROXY=1`（在 Caddy 后面，来源 IP 可信），按“IP + 用户名”限流，同一 IP 累计错 20 次也锁。限流状态在内存里，重启清零；**【真用】**多台应用服务器时要换成数据库或 Redis，对外开放的话再加验证码。
12. **性能**：单台 4 核实测 10 并发看总部看板 p50 约 1 秒、30 并发约 2.7 秒、0 错误，单进程 Node 是瓶颈。10 家店够用；**【真用】**到 50 家店、上千人时要多开几个应用实例让 Caddy 分流，或换更大的机器，总部看板和收银日报做缓存或预先汇总。压测方法：`docker compose run --rm -e LOAD_BASE=http://app:3000 tools pnpm load-test 10 10`（见 `scripts/load-test.ts`）。
13. **服务器安全**：安全组只开 80、443 和 SSH；SSH 只允许密钥登录；系统定期更新（见《服务器与备案指引》）。
15. **企业微信（只有要真对接时）**：
    - 前提：企业微信企业已注册（未认证的企业全公司最多加 100 个客户、部分接口受限）；回调地址要公网域名（不能写 IP）。
    - 企业微信后台建一个自建应用，记下 AgentId 和 Secret；在“客户联系”里把它设为“可调用接口的应用”；应用的可见范围包含所有店员。
    - 应用里配“企业可信 IP”填服务器公网 IP（2022 年以后新建的应用不配调不了接口，报 60020）。

## 结构

一台服务器、一个 `docker compose`：

| 服务 | 干什么 |
|---|---|
| `db` | PostgreSQL 17，数据存在 `pgdata` 卷里 |
| `app` | 本仓库的 Next.js 应用（`Dockerfile` 三段构建，standalone 输出）；带健康检查（`/api/health`） |
| `caddy` | 反向代理 + 访问日志；`SITE_ADDRESS` 是 `:80` 时用 IP 访问，是域名时自动申请 HTTPS 证书 |
| `backup` | 每天 03:00 用 `pg_dump` 备份、`BACKUP_PASSPHRASE` 加密后放到 `./backups`（`.dump.enc`，只有属主能读），写完马上解开整份读一遍核对，坏的当场删掉报失败；留 14 天（`docker/backup.sh`，镜像 `docker/backup.Dockerfile` 多装了 openssl） |
| `tools` | 平时不启动；跑迁移、灌演示数据、对账、每日任务（`pnpm daily`）时临时用 |

环境变量（都写在服务器上的 `.env`，不进仓库）：

| 变量 | 说明 |
|---|---|
| `POSTGRES_PASSWORD` | 数据库所有者 `erp` 的密码（迁移、灌数据、对账、备份用），随机长串 |
| `APP_DB_PASSWORD` | 应用连库的业务账号 `erp_app` 的密码：只能增删改查，改不了表结构（口径第 20 节） |
| `READONLY_DB_PASSWORD` | 只读账号 `erp_readonly` 的密码（以后查数、报表用） |
| `BACKUP_PASSPHRASE` | 备份加密口令；没配备份服务拒绝启动；**另外离线存一份** |
| `SESSION_SECRET` | 登录令牌签名密钥，至少 32 个字符 |
| `DATA_ENCRYPTION_KEY`、`DATA_INDEX_KEY` | 个人信息加密钥匙（口径第 20 节）：手机号、身份证号的密文和指纹，各 32 字节 base64；**另外离线存一份** |
| `SITE_ADDRESS` | `:80` 或域名 |
| `DEMO_MODE` | 必填：`1` 演示站，`0` 真用；不写应用拒绝启动，写 1 启动时打提醒 |
| `WECOM_ENABLED` | `1` 真对接企业微信；不写或 `0`：演示站是模拟模式，真用时整个模块不显示 |
| `WECOM_CORP_ID`、`WECOM_APP_SECRET`、`WECOM_AGENT_ID` | 企业 ID、自建应用的 Secret 和 AgentId（只用这一个 Secret） |
| `WECOM_CALLBACK_TOKEN`、`WECOM_CALLBACK_AES_KEY` | 回调的 Token 和 43 位 EncodingAESKey |

## 第一次部署

```bash
# 1. 服务器上装 Docker（Ubuntu 24.04）
curl -fsSL https://get.docker.com | sh

# 2. 拉代码
git clone https://github.com/2770419748-lgtm/dianyoushu-erp.git && cd dianyoushu-erp

# 3. 写 .env（不进仓库）
# 七个随机串各生成一个（不能重复用同一个）：前三个数据库密码用 openssl rand -hex 32，后四个用 openssl rand -base64 32；
# 最后三个另外离线存一份（见上线前检查清单第 2 条）。数据库密码要在第一次 up -d db 之前定好：库建好以后再改 .env，库里的密码不会跟着变
cat > .env <<'ENV'
POSTGRES_PASSWORD=换成 openssl rand -hex 32 生成的
APP_DB_PASSWORD=换成 openssl rand -hex 32 生成的
READONLY_DB_PASSWORD=换成 openssl rand -hex 32 生成的
SESSION_SECRET=换成随机串
BACKUP_PASSPHRASE=换成随机串
DATA_ENCRYPTION_KEY=换成随机串
DATA_INDEX_KEY=换成随机串
SITE_ADDRESS=:80
DEMO_MODE=1
ENV

# 4. 起数据库（第一次初始化时自动建 erp_app、erp_readonly 两个账号）、建表；演示站再灌演示数据（约 1 分钟）
docker compose up -d db
docker compose run --rm tools pnpm exec prisma migrate deploy
docker compose run --rm tools pnpm db:reset      # 只有演示站跑；DEMO_MODE=0 时会拒绝
docker compose run --rm tools pnpm tenant:init --name "某某通讯"   # 只有真用（DEMO_MODE=0）跑：开户，见下面

# 5. 起应用、Caddy、备份
docker compose up -d --build app caddy backup
docker compose ps                                  # app 要显示 healthy
curl -s http://127.0.0.1/api/health                # {"ok":true}
```

浏览器打开 `http://服务器IP`：演示站用 README 里的演示账号登录，真用的用开户时打印的 `admin` 和初始密码登录（登录 cookie 会按实际协议决定要不要加 Secure，纯 http 也能登录；上了 HTTPS 后自动加）。应用起不来时先看 `docker compose logs app`：配置不合格（会话密钥太短、还是占位值、没配数据库）会打印“配置不合格，拒绝启动”和具体原因。

## 一台服务器放几家客户（正式卖用这个，口径第 24 节）

上面“第一次部署”是一台服务器只跑一套（演示站自己用）。卖给客户以后一家一套、共用一台服务器，用 `deploy/` 下的脚本，2026-10-23 写好、在 CI 里按“两家客户”整套真跑过（`deploy/drill.sh`：开户、子域名访问、升级、坏版本自动回滚、手动回滚、定时任务、恢复演练、批量升级、巡检告警、异地备份）。

```bash
# 目录：/srv/erp/app 代码，/srv/erp/tenants/<代号>/ 每家的 .env 和备份，/srv/erp/proxy/sites/ 共享 Caddy 的站点
sudo mkdir -p /srv/erp && cd /srv/erp && sudo git clone https://github.com/2770419748-lgtm/dianyoushu-erp.git app
cd /srv/erp/app && sudo git checkout <要发的提交或标签> && sudo deploy/build.sh           # 打这个版本的三个镜像，打印版本号
sudo deploy/tenant-new.sh demo demo.你的域名 <版本> --demo                                 # 演示站（灌演示数据）
sudo deploy/tenant-new.sh mouxie mouxie.你的域名 <版本> --name "某某通讯"                    # 一家客户：开户，打印 admin 初始密码一次
sudo deploy/deploy.sh demo <新版本>                                                         # 升级（22 点以后；白天加 --force），失败自动回滚
sudo deploy/upgrade-all.sh <新版本>                                                         # 演示站跑满 20 小时后升所有客户，一家失败就停
sudo deploy/rollback.sh mouxie                                                              # 手动回到上一个版本
```

- 每家的 `.env` 由 `tenant-new.sh` 随机生成（600），里面 `DATA_ENCRYPTION_KEY`、`DATA_INDEX_KEY`、`BACKUP_PASSPHRASE` 开户当天离线存一份（见上线前检查清单第 2 条）。
- 每家用自己的 compose 项目（`erp-<代号>`），库、备份卷、备份目录都分开；进某家的工具容器：`source /srv/erp/app/deploy/lib.sh && dc mouxie run --rm tools pnpm db:check`。
- 升级：备份 → 用新版本迁移 → 换应用 → 等健康检查（最多 2 分钟）→ 对账。数据库迁移只加不删，回滚只换应用；要回到升级前的数据用升级前那份备份恢复（见“恢复演练”）。
- 定时任务、告警、异地备份、日志轮转的模板：`deploy/crontab.example`、`deploy/ops.env.example`、`deploy/logrotate.example`。

## 恢复演练

在临时库里恢复，不动正在用的库：

备份是加密的（口径第 20 节），先用 `BACKUP_PASSPHRASE` 解开再恢复；解开的明文文件用完就删。恢复到哪台服务器，`.env` 里的 `DATA_ENCRYPTION_KEY`、`DATA_INDEX_KEY` 都要用原来那两把（应用启动时会核对，对不上拒绝启动）：

```bash
docker compose exec backup sh -c 'openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -pass env:BACKUP_PASSPHRASE -in /backups/某个备份.dump.enc -out /tmp/restore.dump'
docker compose exec db createdb -U erp restore_check
docker compose exec backup sh -c 'pg_restore -h db -U erp -d restore_check --no-owner /tmp/restore.dump && rm /tmp/restore.dump'
docker compose exec db psql -U erp -d restore_check -c "select count(*) from sales_orders"
docker compose exec db dropdb -U erp restore_check
```

真出事要覆盖正式库：先 `docker compose stop app`，再把上面的 `-d restore_check` 换成 `-d dianyoushu_erp --clean --if-exists`，恢复完 `docker compose start app`。
