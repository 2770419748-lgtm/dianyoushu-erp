# 取舍记录

每条三句话：选了什么、为什么、代价是什么。面试被问“为什么这么做”时照这个讲。

## 技术选型

**为什么选 Next.js 全栈，不做前后端分离**
一个人维护，前后端放在一个 TypeScript 仓库里，页面和服务端共用类型，改一个字段编译器就能把两边都查出来。页面提交走 Server Function，省掉了一层手写接口和接口文档，部署也只有一个进程。代价是和 Next.js 绑得比较深；所以业务规则全放在 `src/server/` 的服务层，不写在页面里，真要拆成独立后端时搬服务层就行。

**为什么选 PostgreSQL**
进销存最怕数据对不上，需要事务、唯一约束、外键这些数据库本身就能保证的东西。串号全局唯一、日结一店一天一条，都是用数据库的唯一索引兜底，不只靠代码判断。看板的统计用 SQL 直接聚合，1.2 万单在 0.5 秒内出结果。

**为什么用 Prisma**
表结构写在一个文件里，自动生成带类型的查询代码，字段写错编译就报错。迁移文件进仓库，谁拉代码都能一条命令建出一样的表。复杂的统计查询（看板）不用它的查询构造，直接写 SQL，用它的参数化防注入。

**为什么用 Ant Design**
ERP 页面主要是表格、表单、弹窗，Ant Design 这些组件齐全，中文文档全，国内后台系统最常见。表格自带分页、横向滚动，手机上也能看。代价是包比较大、样式是运行时注入的，所以 CSP 的样式部分只能放宽。

**为什么登录自己写，不用 Auth.js**
只有账号密码一种登录方式，自己写也就是 bcrypt 存哈希、签一个 JWT 放进 httpOnly cookie，代码少、每一行都讲得清。限流放进程内存里，单进程部署够用，重启清零是已知取舍。令牌不依赖 cookie 校验，以后做 App 改成请求头传就能复用。

## 业务规则

**为什么金额用整数“分”**
小数在计算机里有精度误差，0.1 + 0.2 不等于 0.3，收银对账差一分都不行。所有金额存整数分，只在显示时除以 100。拆分收款、退款分摊这些计算全在整数上做；退款按优惠比例分摊时四舍五入到分，且不能超过“实付 − 已退”，规则都在 `src/server/sales/payments.ts` 的纯函数里，有单元测试。

**为什么库存不直接改余额，而是走流水**
每一次增减（入库、调拨、开单、退货、盘点）都写一条流水，余额只是流水的累计。这样任何一台机器从入库到卖出每一步都查得到，余额对不上时能从流水算回来。模拟数据生成完会自检“余额 = 流水累计”，不为 0 就算失败。

**为什么单据只作废不删除**
删了就没法对账，也查不出是谁动的。作废会恢复库存、写反向流水、记录谁什么时候为什么作废。日结确认后当天的单据锁定，连作废都不行，要先由总部撤销日结。

**并发怎么防：条件写入 + 数据库约束 + 同店同日排队**
两个店员同时卖同一台机器，如果代码是“先读状态、判断在库、再改成已售”，两边都会读到“在库”、都卖成功。现在改机器状态时把“状态还是刚才读到的那个”写进更新条件，改到 0 行就说明被别人抢先了，整单回滚；配件出库用“余额够才减”的原子更新，数据库上再加“余额不能为负”的检查约束兜底。开单、作废、退货和日结确认对同一家店同一天用 PostgreSQL 的事务级咨询锁排队，没有用全库“可串行化”隔离级别，因为那样所有门店都要互相等、还要处理重试。

**登录限流：直接对外按用户名，在反向代理后面按 IP + 用户名**
没有反向代理时请求里的“来源 IP”可以伪造，按 IP 限流等于没限，所以只按用户名锁，代价是别人可以故意输错把某个账号锁住。部署在 Caddy 后面时来源 IP 由 Caddy 写入、可信（`TRUST_PROXY=1`），就按“IP + 用户名”锁，再加一条同一 IP 累计错 20 次锁 IP，别人乱试锁不住真正的员工。限流状态在内存里，单机够用，多台机器要换数据库或 Redis。

**CSP 用 nonce，样式放宽**
App Router 会往页面里写内联脚本，只写 `script-src 'self'` 会把整个页面弄坏；所以请求入口每次生成随机 nonce，Next.js 自动加到自己的脚本上，别的脚本不执行。样式放宽成 `'unsafe-inline'`，因为 Ant Design 是运行时注入样式的，样式被注入的危害远小于脚本。

**性能：先单机，按规模再扩**
单台 4 核实测（2026-10-18）：10 并发看总部看板 p50 约 1 秒、30 并发约 2.7 秒，0 错误；本机笔记本 10 并发看板约 1.4 秒、3 个月收银日报约 3.8 秒。单进程 Node 是瓶颈。10 家店用不着优化；到 50 家店、上千人时多开几个应用实例让 Caddy 分流，总部看板和收银日报改成缓存或每天预先汇总。压测脚本 `scripts/load-test.ts`。

**演示版接受、真用前要评估的几处**
总部没有岗位分离和二次验证；客户表全公司共享（手机号脱敏）；手机号明文存库，备份里也是明文；数据库账号是容器里的超级用户；操作日志和流水不归档；清登录 cookie 的地址是 GET，别的网站能让人被登出；没有自动部署和回滚脚本，权限矩阵和退货、调拨、盘点只有服务层测试、没有端到端测试。都列在 `docs/部署.md` 的上线前检查清单里。

**到期日：先加月、再减一天，月底起保少保一天**
到期日 = 生效日 + N 个月 − 1 天，目标月没有那一天时先取当月最后一天再减一天，所以 1 月 28～31 日起保 1 个月都到 2 月 27 日。这样一条规则覆盖所有日期，2 月、闰年都不用特殊处理，单元测试好写。代价是月底起保的客户少保一两天，演示版接受（2026-10-20 坤总确认保持现状）。

**售后维修：先做主线，维修配件不走库存**
接件、检测报价、维修、取机结算是门店每天都要用的；备用机、外送厂家、维修配件进销存、退换机审核这些九机 OA 里有，但每一项都是一条独立链路，这一版不做。维修配件费手填，不从库存扣，所以维修毛利靠店员填的维修成本，不是配件的实际进价。真要管配件，下一步是把屏幕、电池建成小件、维修时出库。

**客户的机器不算门店库存**
客户拿来修的机器所有权是客户的，接件、维修、取机都不改机器状态、不写库存流水，库存数和对账不受影响；“串号联动”做成按码找到机器、带出购买记录和保修、碎屏险，机器详情页能看到维修记录。代价是店里“手上有几台客户的机器”要看维修单列表（进行中 + 待取机），不在库存页里。

**保修按本店开单日算 12 个月，屏幕、进水不保**
官方保修一般一年，人为损坏不保。演示版不对接厂家，保修、碎屏险、延保的单店里先垫成本，不做向厂家、保险公司的结算；碎屏险理赔一次就用掉，延保期内不限次数。

**运营商业务：只做导入和模拟，不接运营商系统**
移动、联通、电信的渠道系统都不对门店开放接口，门店实际是在渠道系统里办、月初导出结算表格。所以这一版的真路子是“店员手动确认开通 + 总部导入结算单 CSV 对账”，演示里用两个模拟器（同步状态、生成结算单）把流程跑通，只在演示模式能用。代价是对账依赖导出表格的列名，各家表头不一样时要先改成“受理单号、办理号码、业务类型、佣金、返销”再导。

**佣金按笔固定金额，返销按结算单扣**
运营商的佣金政策五花八门（按月租比例、分期返、达量奖励），这一版只按“运营商 × 业务类型”配每笔固定金额，登记时快照下来当预计；实收和返销一律以运营商结算单为准，系统不自己按返销期去算扣回。这样预计和实收的差异就是要找运营商核对的地方。真要按套餐比例算，下一步是在政策里加“按月租 × 比例”一种算法。

**佣金不进日结**
佣金是运营商月底打给公司的钱，不是门店当天收的；客户在店里交的话费、宽带费直接进运营商账户。所以运营商业务不写收款、不进日结和收银日报，只在运营商业务统计里看，员工提成以后由人事模块按实收佣金算。

**延保接在保修后面，从保修到期次日起算**
起初延保和碎屏险一样从开单日起算，1 年延保和 1 年保修完全重叠，非人为故障在这一年里保修总能选，延保永远用不上（演示数据 387 张维修单里延保付的是 0 张）。真实业务里延保就是“官方保修过了再保一年”，2026-10-20 坤总在自检卡片上选了“保修到期次日起算”。到期日算法不变（起算日 + N 个月 − 1 天），只是起算日往后推 12 个月；页面上延保在生效前显示“未生效”。演示数据里加了每家店 4 张一年多前的老单（买机器加延保，那几天补了已确认的日结），这些机器现在拿来修就是延保付。
延保要和机器同一张单买、保本单的机器。不同单买的延保如果按那张单的营业日 + 12 个月起算，机器买了 3 个月才补买延保就会空出 3 个月；真要支持补买，得让店员选客户名下哪台机器、从那台的保修到期次日起算，这一版先不做，开单时直接拦下（2026-10-20 自检复查后定的默认做法）。

**企业微信：先做底座 + 模拟演示，不做真联调**
真对接要已认证的企业主体、备案主体一致的域名和固定服务器 IP，个人现在办不下来；面试也不会当场扫码加企业微信。所以企业微信做成两种模式：真对接的代码写全（加解密、回调、令牌、接口），演示站用模拟的接口，再造一条加密事件走一遍真实的回调处理。代价是真企业微信下的行为没有实测过，上线前要按部署清单联调一遍。

**客户只按开单绑定码绑定，不按手机号猜**
企业微信给不了客户手机号，只有昵称、头像，按昵称猜会错绑，把 A 的保修提醒发给 B。所以开单后生成一张只认这个客户的一次性二维码，扫了才绑。代价是不扫码的客户绑不上，要等员工认领（这一版还没做认领）。

**令牌落库，不加 Redis**
企业微信的令牌 2 小时有效，多个请求同时发现过期会重复去换。没有缓存层，就存在数据库里，刷新时用 PostgreSQL 的事务级咨询锁排队，只有一个请求真去换，其他的拿锁后重读缓存。代价是每次调接口多一次查库，量小，不影响。

**改价不设下限、不要审批**
门店里改价很常见（老客优惠、凑整），每次都等店长批会卡住收银。现在的做法是改价照常，但单据上同时存原价和成交价、改过的标出来、写进操作日志，事后可查。真要管住，下一步是“低于某个比例要店长输密码确认”。

**为什么大件存三个码**
一台手机盒子上有 SN、IMEI1、IMEI2，店员手里拿到哪个扫哪个，系统要都认得。三个码各自全局唯一，主码按 IMEI1、SN、IMEI2 的顺序取，列表和链接统一用主码。不要求三个都填，只录一个也能入库。

## 范围

**为什么不做 App**
门店用手机浏览器打开，加上“添加到主屏幕”全屏打开，已经够用，不用过应用商店审核。一个人同时维护网页和两个原生 App 不划算。路留着：业务都在服务层，扫码封装成一个接口，以后用 Capacitor 套壳时只换扫码实现。

**为什么不做人事（考勤、排班、工资、绩效）**
和进销存这条主链路没关系，做了也不能让演示更完整。各家公司规则差别大，工资又是敏感数据，演示版不适合碰。真要做先接排班，因为它能和看板的员工业绩对上。

**为什么不做售后、财务总账、审批流、会员营销**
每一个都是一条独立的长链路，做半截不如不做，演示时还容易被问倒。系统里的“后续规划”页列了每一项为什么没做、以后从哪儿接。演示版只做门店每天离不开的：进货、串号库存、调拨盘点、开单收银、回收、日结、看板。

**为什么不做离线**
ERP 数据要实时，两个店员同时卖同一台机器必须有一个失败，离线下单会把这件事推迟到联网时才发现。PWA 只做了“添加到桌面”，没做离线缓存。门店断网时用纸质单据记，联网后补录，这是大多数门店现在的做法。

**为什么服务器还没买**
现在还没开始找工作，服务器和域名按月花钱，备案要 1 到 3 周。所有要服务器的事集中放到“找工作前再做”，第一次面试前约 3 周开始。没上线前用本机演示，手机测试用本机临时 HTTPS。
