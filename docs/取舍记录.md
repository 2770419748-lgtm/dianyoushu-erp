# 取舍记录

每条三句话：选了什么、为什么、代价是什么。面试被问“为什么这么做”时照这个讲。

## 技术选型

**为什么选 Next.js 全栈，不做前后端分离**
一个人维护，前后端放在一个 TypeScript 仓库里，页面和服务端共用类型，改一个字段编译器就能把两边都查出来。页面提交走 Server Function，省掉了一层手写接口和接口文档，部署也只有一个进程。代价是和 Next.js 绑得比较深；所以业务规则全放在 `src/server/` 的服务层，不写在页面里，真要拆成独立后端时搬服务层就行。

**为什么选 PostgreSQL**
进销存最怕数据对不上，需要事务、唯一约束、外键这些数据库本身就能保证的东西。串号全局唯一、日结一店一天一条，都是用数据库的唯一索引兜底，不只靠代码判断。看板的统计用 SQL 直接聚合，1.2 万单在 0.5 秒内出结果。

**为什么用 Prisma**
表结构写在一个文件里，自动生成带类型的查询代码，字段写错编译就报错。迁移文件进仓库，谁拉代码都能一条命令建出一样的表。复杂的统计查询（看板）不用它的查询构造，直接写 SQL，用它的参数化防注入。

**为什么用 Ant Design**
ERP 页面主要是表格、表单、弹窗，Ant Design 这些组件齐全，中文文档全，国内后台系统最常见。表格自带分页、横向滚动，手机上也能看。代价是包比较大、样式是运行时注入的，所以 CSP 的样式部分只能放宽。

**为什么登录自己写，不用 Auth.js**
只有账号密码一种登录方式，自己写也就是 bcrypt 存哈希、签一个 JWT 放进 httpOnly cookie，代码少、每一行都讲得清。限流放进程内存里，单进程部署够用，重启清零是已知取舍。令牌不依赖 cookie 校验，以后做 App 改成请求头传就能复用。

## 业务规则

**为什么金额用整数“分”**
小数在计算机里有精度误差，0.1 + 0.2 不等于 0.3，收银对账差一分都不行。所有金额存整数分，只在显示时除以 100。拆分收款、退款分摊这些计算全在整数上做；退款按优惠比例分摊时四舍五入到分，且不能超过“实付 − 已退”，规则都在 `src/server/sales/payments.ts` 的纯函数里，有单元测试。

**为什么库存不直接改余额，而是走流水**
每一次增减（入库、调拨、开单、退货、盘点）都写一条流水，余额只是流水的累计。这样任何一台机器从入库到卖出每一步都查得到，余额对不上时能从流水算回来。模拟数据生成完会自检“余额 = 流水累计”，不为 0 就算失败。

**为什么单据只作废不删除**
删了就没法对账，也查不出是谁动的。作废会恢复库存、写反向流水、记录谁什么时候为什么作废。日结确认后当天的单据锁定，连作废都不行，要先由总部撤销日结。

**并发怎么防：条件写入 + 数据库约束 + 同店同日排队**
两个店员同时卖同一台机器，如果代码是“先读状态、判断在库、再改成已售”，两边都会读到“在库”、都卖成功。现在改机器状态时把“状态还是刚才读到的那个”写进更新条件，改到 0 行就说明被别人抢先了，整单回滚；配件出库用“余额够才减”的原子更新，数据库上再加“余额不能为负”的检查约束兜底。开单、作废、退货和日结确认对同一家店同一天用 PostgreSQL 的事务级咨询锁排队，没有用全库“可串行化”隔离级别，因为那样所有门店都要互相等、还要处理重试。

**登录限流：直接对外按用户名，在反向代理后面按 IP + 用户名**
没有反向代理时请求里的“来源 IP”可以伪造，按 IP 限流等于没限，所以只按用户名锁，代价是别人可以故意输错把某个账号锁住。部署在 Caddy 后面时来源 IP 由 Caddy 写入、可信（`TRUST_PROXY=1`），就按“IP + 用户名”锁，再加一条同一 IP 累计错 20 次锁 IP，别人乱试锁不住真正的员工。限流状态在内存里，单机够用，多台机器要换数据库或 Redis。

**CSP 用 nonce，样式放宽**
App Router 会往页面里写内联脚本，只写 `script-src 'self'` 会把整个页面弄坏；所以请求入口每次生成随机 nonce，Next.js 自动加到自己的脚本上，别的脚本不执行。样式放宽成 `'unsafe-inline'`，因为 Ant Design 是运行时注入样式的，样式被注入的危害远小于脚本。

**性能：先单机，按规模再扩**
单台 4 核实测（2026-10-18）：10 并发看总部看板 p50 约 1 秒、30 并发约 2.7 秒，0 错误；本机笔记本 10 并发看板约 1.4 秒、3 个月收银日报约 3.8 秒。单进程 Node 是瓶颈。10 家店用不着优化；到 50 家店、上千人时多开几个应用实例让 Caddy 分流，总部看板和收银日报改成缓存或每天预先汇总。压测脚本 `scripts/load-test.ts`。

**演示版接受、真用前要评估的几处**
总部没有岗位分离和二次验证；客户表全公司共享（手机号脱敏）；手机号明文存库，备份里也是明文；数据库账号是容器里的超级用户；操作日志和流水不归档；清登录 cookie 的地址是 GET，别的网站能让人被登出；没有自动部署和回滚脚本，权限矩阵和退货、调拨、盘点只有服务层测试、没有端到端测试。都列在 `docs/部署.md` 的上线前检查清单里。

**到期日：先加月、再减一天，月底起保少保一天**
到期日 = 生效日 + N 个月 − 1 天，目标月没有那一天时先取当月最后一天再减一天，所以 1 月 28～31 日起保 1 个月都到 2 月 27 日。这样一条规则覆盖所有日期，2 月、闰年都不用特殊处理，单元测试好写。代价是月底起保的客户少保一两天，演示版接受（2026-10-20 坤总确认保持现状）。

**售后维修：先做主线，维修配件不走库存**
接件、检测报价、维修、取机结算是门店每天都要用的；备用机、外送厂家、维修配件进销存、退换机审核这些九机 OA 里有，但每一项都是一条独立链路，这一版不做。维修配件费手填，不从库存扣，所以维修毛利靠店员填的维修成本，不是配件的实际进价。真要管配件，下一步是把屏幕、电池建成小件、维修时出库。

**客户的机器不算门店库存**
客户拿来修的机器所有权是客户的，接件、维修、取机都不改机器状态、不写库存流水，库存数和对账不受影响；“串号联动”做成按码找到机器、带出购买记录和保修、碎屏险，机器详情页能看到维修记录。代价是店里“手上有几台客户的机器”要看维修单列表（进行中 + 待取机），不在库存页里。

**保修按本店开单日算 12 个月，屏幕、进水不保**
官方保修一般一年，人为损坏不保。演示版不对接厂家，保修、碎屏险、延保的单店里先垫成本，不做向厂家、保险公司的结算；碎屏险理赔一次就用掉，延保期内不限次数。

**运营商业务：只做导入和模拟，不接运营商系统**
移动、联通、电信的渠道系统都不对门店开放接口，门店实际是在渠道系统里办、月初导出结算表格。所以这一版的真路子是“店员手动确认开通 + 总部导入结算单 CSV 对账”，演示里用两个模拟器（同步状态、生成结算单）把流程跑通，只在演示模式能用。代价是对账依赖导出表格的列名，各家表头不一样时要先改成“受理单号、办理号码、业务类型、佣金、返销”再导。

**佣金按笔固定金额，返销按结算单扣**
运营商的佣金政策五花八门（按月租比例、分期返、达量奖励），这一版只按“运营商 × 业务类型”配每笔固定金额，登记时快照下来当预计；实收和返销一律以运营商结算单为准，系统不自己按返销期去算扣回。这样预计和实收的差异就是要找运营商核对的地方。真要按套餐比例算，下一步是在政策里加“按月租 × 比例”一种算法。

**国补：开单立减、审核到账靠导入，平台做成模拟**
各省国补平台各不相同，也不对门店系统开放；门店实际是顾客在云闪付等平台领资格、收银时核销，事后在平台上传发票和串号照片、等审核和打款。所以这一版系统负责门店这一侧：按政策算补贴、校验每人每类一台、记一笔“国补立减”、跟踪每张国补单直到到账，平台那一侧用“导入平台结果表格”接，演示里用模拟器。代价是资格码在真用时只能记下来、不能当场核验（核验在支付终端上做）。

**国补：一个资格码补一台，被驳回的门店自己承担**
平台的资格是一个品类一张券，一次核销一台机器，所以系统一张单只补一台（挑补贴最多的）；要同时补手机和平板就分两张单开。被平台驳回的补贴，资料问题可以改了重新提交；真收不回来的算门店损失，不找顾客补缴（找顾客要钱的流程复杂、体验差，演示版不做）。

**发票：门店申请、总部开具，开票接口做成模拟**
数电票要公司的税务数字账户和开票权限，个人演示办不下来；门店实际流程也是门店登记、财务统一开。所以系统管申请、明细和税额、状态（开具、红冲、到店），号码在演示里模拟生成，真用时财务在电子税务局开好回来登记。代价是没有发票版式文件（PDF），顾客拿的是税务平台发的那张。

**发票：一单一张在办的，不合并不拆分；国补、以旧换新不减发票金额**
合并多张单开一张、一张单拆成几张，在门店里少见，状态和红冲会变复杂，这一版不做。国补立减和以旧换新抵扣都是收款方式，发票按成交价开（国补平台审核要的正是全额发票）。

**企微侧边栏：自己的票，不复用 ERP 登录**
PRD 原来写“用现有 token.ts 签发会话”，那样签出来的就是一张完整的 ERP 登录票，在企业微信里点一下就能进所有页面。现在侧边栏单独一个 cookie（只在 /wecom-app 下发送、2 小时过期），签名密钥从 SESSION_SECRET 派生另一把，票里写明用途；ERP 那边验签必然失败，还额外拒收带用途的票。代价是侧边栏要自己做一遍“票换人”（核对在职、会话版本、企业微信账号），多几行代码。

**智能提醒：程序找事、算数，模型只写话**
评估里定的做法：规则是程序写的，能写测试、能对账；大模型只排先后、写成人话，写出来的每个数字都要在程序给的清单里。先做不接模型也能跑的一期（模板版今日待办 + 消息 + 推群），模型挂了、没网、欠费都照常发模板版。代价是规则要一条条写，覆盖不了“自由提问”，问数助手不在这一版。

**智能提醒：模型只回 JSON，程序拼 markdown、查每个数字**
让模型按“序号 + 一句话”回 JSON，而不是直接写一整段 markdown：序号能核对它没漏、没重复，漏掉的程序按自己的说法补上；正文里出现的每个数字都要在交给它的清单里，有一个不在就整份改发模板版。代价是模型不能自己算“合计”“差多少”，这些数字要程序先算好放进清单。

**智能提醒：演示站用模拟模型**
没配大模型 key 的演示站，用一个“模拟模型”：程序读清单、按轻重和类别排序、在说明后面加一句固定的建议，回和真模型一样的 JSON，走同一套解析和校验。这样面试现场没网、没 key 也能把整条链路演出来，页面上标“模拟模型”，不冒充 AI。

**智能提醒：群机器人地址只认企业微信官方的**
群机器人地址由总部在组织管理里填，服务器会去请求它；如果随便什么地址都收，就能让服务器去访问内网（SSRF）。所以服务层和数据库都只认 https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=… 这一种，地址带密钥，页面只显示有没有填。

**客户继承：停用员工不等继承**
PRD 原来写“继承失败就不让停用账号”，那样人走了账号还能登录。现在停用马上生效，客户继承另外挂成任务：企业微信要求先在后台删掉这个人才能离职继承，系统每天看删了没、删了就提交、再查结果。代价是离职当天到删人这段时间，客户还挂在离职员工名下，客户继承页会列出来提醒。

**微信客服：规则答复，不用大模型；没绑定的不答保障**
客服先按关键词答（营业时间地址、保修、理赔、价格库存、我的保障），答不了或客户要人工就转人工。规则答得窄，但不会胡编价格和政策，演示也不用配模型的钥匙；大模型放到第 7 项 AI 统一接。“我的保障”只答在门店扫过开单二维码、或员工认领过的客户；让客户报手机号后 4 位核对太容易被冒充（只有一万种），所以没绑定的一律转人工，代价是新客户问保障要等人工。

**微信客服：客服渠道的客户 id 当成和客户联系的同一套**
官方没写明两套 id 是不是一样，这一版按“客服拉回来的客户 id 去找绑定过的客户档案”来认人：对上了答保障，对不上就当没绑定、转人工，最坏是多转人工，不会答错人。等有真企业实测后再定要不要加别的认人办法。

**企微侧边栏的演示用 iframe**
模拟的企业微信聊天窗口里，侧边栏用 iframe 打开真正的 /wecom-app 页面，这样演示的就是真页面、真的两套登录。全站原来禁止被任何页面框住（X-Frame-Options: DENY），现在只对 /wecom-app 放宽到“本站可以框”，别的页面不变。真机的企业微信侧边栏是独立的网页窗口，不靠这个放宽。

**审批：存“要做的事”，批了再按当时的数据做一遍**
另一种做法是先把单据建成“待审批”状态（库存先锁住），批了再生效；但开单、退货、调拨、盘点各有各的状态机，每一种都要加一个待审批状态，改动面大，还会把机器锁在一张可能被驳回的单上。现在的做法是把这件事的全部输入存进审批单，批的时候以发起人身份、按当时的数据再执行一遍（和他自己点提交走同一个服务函数，只是跳过审批检查），做不成就写明原因让他重来。代价是批之前机器不锁，审批期间可能被别人卖掉。门店里开单审批一般就是顾客在店里等、店长手机上批，时间很短，可以接受。

**审批：开单的价格在提交时写死**
另一种做法是批的时候按当时的价格开、开完和申请时的应收比一比，不一样就算“批了没做成”。但顾客在店里等的就是申请时说好的那个价，审批人批的也是这个价；所以提交时把每行成交价写进审批单，批出来照这个价开，期间门店改价不影响这一单。代价是门店降价后批出来的单比新价贵，店员要注意顾客是不是在改价后才成交的。

**审批：只有一级，规则默认全关**
多级审批（店长批完再总部批）、会签、超时自动通过在门店场景里用得少，这一版只做一级：规则决定谁批，发起人角色够得上审批人的不用批。规则默认全关，和以前“改价不设下限、不要审批”的口径一致，总部要管再打开。

**佣金不进日结**
佣金是运营商月底打给公司的钱，不是门店当天收的；客户在店里交的话费、宽带费直接进运营商账户。所以运营商业务不写收款、不进日结和收银日报，只在运营商业务统计里看，员工提成以后由人事模块按实收佣金算。

**延保接在保修后面，从保修到期次日起算**
起初延保和碎屏险一样从开单日起算，1 年延保和 1 年保修完全重叠，非人为故障在这一年里保修总能选，延保永远用不上（演示数据 387 张维修单里延保付的是 0 张）。真实业务里延保就是“官方保修过了再保一年”，2026-10-20 坤总在自检卡片上选了“保修到期次日起算”。到期日算法不变（起算日 + N 个月 − 1 天），只是起算日往后推 12 个月；页面上延保在生效前显示“未生效”。演示数据里加了每家店 4 张一年多前的老单（买机器加延保，那几天补了已确认的日结），这些机器现在拿来修就是延保付。
延保要和机器同一张单买、保本单的机器。不同单买的延保如果按那张单的营业日 + 12 个月起算，机器买了 3 个月才补买延保就会空出 3 个月；真要支持补买，得让店员选客户名下哪台机器、从那台的保修到期次日起算，这一版先不做，开单时直接拦下（2026-10-20 自检复查后定的默认做法）。

**企业微信：先做底座 + 模拟演示，不做真联调**
真对接要已认证的企业主体、备案主体一致的域名和固定服务器 IP，个人现在办不下来；面试也不会当场扫码加企业微信。所以企业微信做成两种模式：真对接的代码写全（加解密、回调、令牌、接口），演示站用模拟的接口，再造一条加密事件走一遍真实的回调处理。代价是真企业微信下的行为没有实测过，上线前要按部署清单联调一遍。

**客户只按开单绑定码绑定，不按手机号猜**
企业微信给不了客户手机号，只有昵称、头像，按昵称猜会错绑，把 A 的保修提醒发给 B。所以开单后生成一张只认这个客户的一次性二维码，扫了才绑。代价是不扫码的客户绑不上，要等员工认领（这一版还没做认领）。

**令牌落库，不加 Redis**
企业微信的令牌 2 小时有效，多个请求同时发现过期会重复去换。没有缓存层，就存在数据库里，刷新时用 PostgreSQL 的事务级咨询锁排队，只有一个请求真去换，其他的拿锁后重读缓存。代价是每次调接口多一次查库，量小，不影响。

**改价不设下限、不要审批**
门店里改价很常见（老客优惠、凑整），每次都等店长批会卡住收银。现在的做法是改价照常，但单据上同时存原价和成交价、改过的标出来、写进操作日志，事后可查。真要管住，下一步是“低于某个比例要店长输密码确认”。

**为什么大件存三个码**
一台手机盒子上有 SN、IMEI1、IMEI2，店员手里拿到哪个扫哪个，系统要都认得。三个码各自全局唯一，主码按 IMEI1、SN、IMEI2 的顺序取，列表和链接统一用主码。不要求三个都填，只录一个也能入库。

**店长只是不能改自己今天和以前的班**
问题出在事后改：把自己过去的缺勤改成休息，8d 按缺勤扣钱就等于给自己免扣，补卡“不能给自己补”也被绕过。所以今天和以前的自己的班只能总部改。以后的班照常自己排：排班本来就是店长的日常工作，每周都找总部太麻烦；排了以后的休息，表上大家都看得到，不是事后改账。

**按那天在哪家店算，不按现在在哪家店**
调了店的人，以前的班、考勤要是跟着人走，新店的统计里会多出他在老店的日子，8e 门店的人工成本也会算错店。所以每一天都看那天的排班门店（没排班看打卡记的门店）。代价是统计要多查一层“这天算哪家”，工资条按人整月算，分到门店时再按上班天数分。

**利润表的运营商佣金用登记时的预计佣金**
运营商结算单要到下个月才出，还会返销、扣回；要是利润表用结算后的实收，过去月份的利润会一直变。所以这里用登记时按政策记下的预计佣金，和门店当月的努力对得上；结算差额、返销在运营商对账页看。真要按实收算，换成结算月份的已结算金额就行。

**工资只到应发，不算社保个税**
社保、个税各地规则不同，还牵涉专项附加扣除，算错了是真金白银的事；这一版只到“应发”，财务拿着应发去另算实发。工资条发布后数字锁定，要改整月作废重算，留着作废记录和原因，不做单张改发布后的数。

**入职、离职当月按在职天数折算基本工资**
口径只说了缺勤扣款，没说月中入职、离职怎么算。不折算的话，月底才来的人也拿整月基本工资。默认按自然日折算（基本工资 × 在职天数 ÷ 当月天数），写进了口径的默认做法，坤总要按别的算法（比如按应出勤天数）再改。

**报销按付款日期算进门店费用，不按发生日期**
口径写的是“付完才算进门店当月的费用”。按发生日期算的话，上个月的单这个月才付，上个月的利润表在关账以后还会变；按付款日期算，一个月过完数字就定了，和财务实际出钱的月份也对得上。代价是费用会晚一个月体现，口径里写清楚了。

**今日待办：店员看店员版，不放 KPI 和日结**
口径原来写本店一份发给店长和店员，可 KPI 落后那条写着“每天要卖多少元”、日结写着差多少钱，看板和日结页店员都打不开。按现有权限，店员版去掉这两类（门店群里有店员，推的也是店员版），店长版照旧全有。两份命中的一样时店员版直接用店长版写好的，不多调一次模型。坤总要让店员也看 KPI，把这两类从 `MANAGER_ONLY_KINDS` 拿掉就行。

**今日待办：按命中的东西判断变没变，不比成品文字**
原来比的是写出来的文字，可文字里有“等了几小时”“最久压了几天”，过一会儿点“立即生成”就重推、全店消息重标未读，真模型措辞每次不同更是每点必推。现在存一个“命中签名”（种类 + 台数、张数、差额这些关键数字），一样就不重写、不推、不调模型。代价是同一件事只是等得更久了，不会再提醒一次。

**审批：每种事项登记执行器，不在审批里写死**
原来审批服务里有一段按事项分支的代码，加一种事项（请假、报销）就要改审批本身，还容易循环引用。现在每种事项在 `executors.ts` 登记“批到最后一级做什么、驳回撤回做什么、做出来的单在哪儿看、哪些错误算做不成”，审批服务只认这张表。代价是多一层间接，看代码要多跳一个文件。

**两级审批：总部批了第一级就算最后一级**
店长批完转总部，是因为店长的权限不够；总部是最高一级，总部直接批了店长那一级，后面再等一个总部没有意义（第二个总部的人会觉得奇怪“我批谁的”）。所以审批链往后找“比这次批的人级别高的那一级”，找不到就生效。前一级批过的人不能再批后一级，防止同一个人批两次。

**考勤不存结果，按班现算**
迟到、早退、缺卡、缺勤都是由“当天的班 + 打卡 + 批了的假”算出来的，存一份结果就要在改排班、补卡、批假时都记得重算，漏一处就对不上。现在只存排班、打卡、请假三样原始记录，看统计时现算（一家店一个月几百条，很快）；工资条发布时再把当月数字写死。

## 范围

**为什么不做 App**
门店用手机浏览器打开，加上“添加到主屏幕”全屏打开，已经够用，不用过应用商店审核。一个人同时维护网页和两个原生 App 不划算。路留着：业务都在服务层，扫码封装成一个接口，以后用 Capacitor 套壳时只换扫码实现。

**为什么不做人事（考勤、排班、工资、绩效）**
和进销存这条主链路没关系，做了也不能让演示更完整。各家公司规则差别大，工资又是敏感数据，演示版不适合碰。真要做先接排班，因为它能和看板的员工业绩对上。
（2026-10-20 坤总把人事财务 OA 排进第 8 项、从头自建，规则见口径第 19 节；上面是演示版当时的考虑，留着看演变。）

**为什么不做售后、财务总账、审批流、会员营销**
每一个都是一条独立的长链路，做半截不如不做，演示时还容易被问倒。系统里的“后续规划”页列了每一项为什么没做、以后从哪儿接。演示版只做门店每天离不开的：进货、串号库存、调拨盘点、开单收银、回收、日结、看板。

**为什么不做离线**
ERP 数据要实时，两个店员同时卖同一台机器必须有一个失败，离线下单会把这件事推迟到联网时才发现。PWA 只做了“添加到桌面”，没做离线缓存。门店断网时用纸质单据记，联网后补录，这是大多数门店现在的做法。

**为什么服务器还没买**
现在还没开始找工作，服务器和域名按月花钱，备案要 1 到 3 周。所有要服务器的事集中放到“找工作前再做”，第一次面试前约 3 周开始。没上线前用本机演示，手机测试用本机临时 HTTPS。
