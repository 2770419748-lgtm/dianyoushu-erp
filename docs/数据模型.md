# 店有数 ERP：数据模型说明

- 版本：2026-10-16（第 3 天），对应 `prisma/schema.prisma` 和迁移 `20261016102604_business_tables`
- 依据：`docs/业务口径.md` v0；方案文档 6.4 节的每张表都在，另加了盘点、门店售价、入库单明细、单号计数器
- 规矩：表名、列名在数据库里是 snake_case（如 `sales_orders.total_fen`），代码里是驼峰（`salesOrder.totalFen`）；金额整数"分"、字段名以 `Fen` 结尾；数量 `qty`；时间 UTC 存、界面按本地显示；状态用枚举
- 共 40 张表（含 Prisma 自己的迁移记录表则 41 张）；2026-10-20 加了服务权益两张表（迁移 `service_entitlements`）和企业微信六张表（迁移 `wecom_base`），见口径第 12 节；售后维修一张表（迁移 `repair_orders`），见口径第 13 节

## 一、组织与用户（第 1 周已建，本次未改结构）

| 表 | 业务叫法 | 关键字段 | 说明 |
|---|---|---|---|
| `regions` | 区域 | 名称、是否启用 | 一级 |
| `stores` | 门店 | 编码、名称、所属区域、地址、是否启用 | 停用不删 |
| `users` | 员工 / 登录账号 | 账号、密码哈希、姓名、角色、所属门店、所辖区域、是否在职、企业微信账号（唯一，可空） | 角色四选一；店员店长带门店，区域经理带区域 |

## 二、商品主数据

| 表 | 业务叫法 | 关键字段 | 说明 |
|---|---|---|---|
| `categories` | 品类 | 名称、大件/小件（kind）、排序 | 大件按串号，小件按数量，由品类决定 |
| `brands` | 品牌 | 名称 | |
| `product_models` | 型号 | 品牌、品类、名称 | 同品牌下名称唯一；版本差异当不同型号 |
| `skus` | SKU（具体款） | 型号、显示名、颜色、容量、条码、指导价、参考成本、安全库存 | 条码可空但填了必须唯一；安全库存只对小件有意义，门店数量低于它在库存页标红，0 = 不预警（第 5 周加）；`is_service` + `service_months` + `service_kind` 标服务类商品（碎屏险 / 延保 / 其他），服务类必须有 1～120 个月期限和服务种类（数据库 CHECK），不管库存（2026-10-20 加） |
| `store_prices` | 门店售价 | 门店、SKU、售价 | 没记录就按指导价；门店 × SKU 唯一 |

## 三、库存

| 表 | 业务叫法 | 关键字段 | 说明 |
|---|---|---|---|
| `devices` | 串号机器 | 主码 code（唯一，非空）、SN、IMEI1、IMEI2（各自唯一，可空，至少一个）、SKU、当前归属门店、状态、成本、成色、入库单、回收单 | 一台一行；主码 = IMEI1 ?? SN ?? IMEI2，链接和显示用主码，查找时四个列都匹配；状态按口径第 4 节状态机走；成本 = 采购成本或回收估价（三个码是 2026-10-16 坤总定的，迁移 `device_three_codes`） |
| `accessory_stocks` | 配件库存 | 门店、SKU、数量 | 余额表，由流水在同一事务里维护；门店 × SKU 唯一 |
| `stock_ledgers` | 库存流水 | 单据类型、单号、门店、SKU、串号机器、数量正负、变动后余额、状态前/后、操作人、时间 | 每一次增减一条；只改状态的（锁定、转良品）数量记 0 但也有一条，串号追溯就看它 |

库存流水的单据类型（`ledger_doc_type`）：采购入库 +、调拨锁定 0、调拨解锁 0、调拨发出 −、调拨收货 +、盘盈 +、盘亏 −、销售 −、销售作废 +、退货 +、回收入库 +、转良品 0。在途的机器不在任何门店的余额里（发出店已 −，收货店还没 +）。

| `purchase_order_items` | 采购明细 | SKU、数量、单价成本、已到货数量 | 已到货数量由入库单累加，全部到齐采购单变已到货 |
| `goods_receipts` | 入库单 | 单号 RI…、采购单、门店、收货人 | 一次到货一张，可多次 |
| `goods_receipt_items` | 入库明细 | SKU、数量、单价成本 | 大件的数量 = 串号条数，串号本身在 `devices` 里，`devices.goods_receipt_id` 指回入库单 |

## 六、客户、销售、退货、回收

| 表 | 业务叫法 | 关键字段 | 说明 |
|---|---|---|---|
| `customers` | 客户 | 姓名、手机号（唯一）、备注；企业微信外部联系人 id（唯一）、微信昵称、头像、绑定时间 | 列表脱敏显示；企业微信身份只按开单绑定码写入，不按手机号猜 |
| `sales_orders` | 销售单 | 单号 SO…、门店、客户、销售员、状态（已完成/已作废）、营业日、折前合计、整单优惠、应收、关联回收单、日结、作废人/时间/原因 | 应收 = 折前 − 优惠，支付明细合计必须等于应收；日结回填后不可作废 |
| `sales_order_items` | 销售明细 | SKU、串号机器、数量、成交单价、行优惠、行小计、成本快照、已退数量 | 成本快照用来算毛利，不受以后改成本影响 |

| `return_orders` | 退货单 | 单号 RT…、门店、原销售单、客户、经手人、营业日、退款合计、原因、日结 | |
| `return_order_items` | 退货明细 | 原销售明细、SKU、串号机器、数量、退款 | |
| `repair_orders` | 维修单 | 单号 WX…、接件门店、客户、接件人、机器（本系统卖出的才有）、码、机型、购买的销售单和营业日、故障类型和描述、外观附件、状态（已接件/已报价/维修中/待取机/已完结/已作废）、配件费、工时费、维修成本、谁付、用的碎屏险或延保、客户应付、结果、各步时间、取机营业日、日结、作废人和原因 | 客户的机器不算库存，不写库存流水；同一个码同时只有一张没完结的单；收款进取机那天的日结；金额不为负（数据库 CHECK） |

## 方案 6.5 的六条规则在表里怎么落地

| 规则 | 落地 |
|---|---|
| 1 串号全局唯一，状态按状态机走 | `devices` 的 `code`（主码）、`sn`、`imei1`、`imei2` 各自唯一索引；状态是枚举；状态跳转只在 `src/server` 的库存服务里做，服务层按口径第 4 节的表校验，非法跳转拒绝 |
| 2 库存变化走流水，余额能从流水算出 | 大件余额 = `devices` 里状态为在库/良品的台数，每次变动都写 `stock_ledgers`；小件余额表 `accessory_stocks` 只在写流水的同一事务里更新，流水带 `balance_after`，随时可重算核对 |
| 3 开单扣库存、记收款、写流水一个事务 | `sales_orders` + `sales_order_items` + `payments` + `stock_ledgers` + `devices`/`accessory_stocks` 的改动放在一个 `prisma.$transaction` 里 |
| 4 单据不物理删除，只作废留痕 | 采购单、调拨单、盘点单有作废状态和 `voided_at`，谁作废的记在操作日志；销售单还有 `voided_by_id`、`void_reason`；回收单表留了作废状态和 `voided_by_id`、`voided_at`，但这版不做作废；入库单、退货单不作废（录错用盘点或再开一单纠正）。没有任何 delete |
| 5 金额用整数分 | 所有金额列都是整数、以 `_fen` 结尾；汇总用数据库 bigint 求和 |
| 6 权限服务端校验 | 所有查询都经过 `src/server/auth/permissions.ts` 取数据范围再过滤 `store_id`；详见 AGENTS.md |
